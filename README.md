# 食光转盘 · 一起吃什么

面向熟人小组的用餐决策工具：表达底线 → 认可共同候选 → 转盘提议 → 全员确认 → 餐后反馈。

- **正式入口**：https://lavieme.github.io/my-food-wheel/
- **在线服务与备用入口**：https://food-wheel-lavieme.haivivi-8454.chatgpt.site/
- 原版备份分支：`backup/pre-online-2026-10-27`，原始单页另保留在 `legacy/index.html`。

## 和朋友一起使用

1. 在「店铺库」添加真实店铺、预计人均和具体分店地址。
2. 发起饭局，点击「邀请搭子」复制链接。
3. 朋友直接打开链接，各自提交预算和不接受的品类 / 店铺。
4. 所有成员认可共同候选后，由发起人启动转盘。
5. 每个人确认后才算完成；任意成员可提出异议并重新选择。
6. 就餐后由发起人记录「去吃了 / 换了一家 / 没吃成」。

公网模式不需要连接同一个 Wi-Fi，不需要保持开发者电脑运行。没有账户或登录步骤，成员身份通过随机凭证保存在各自浏览器。房间链接仅含房间码，不含成员凭证。

默认店铺为明确标注的示例，价格与地址不能视为真实商家信息。示例店铺禁用地图跳转；实际使用请替换为真实分店。有饮食限制时，请排除无法确认合适的店并向商家核实。

## 当前功能

- 多人饭局 2–8 人；单人选店单独简化流程。
- 预算上限、排除品类和排除店铺均为硬约束，不自动放宽。
- 候选池为空时说明状态，允许主动调整条件或恢复本轮异议店铺。
- 每个候选等概率被选中，服务端统一产生结果。
- 成员或条件变化会清除旧认可；异议会清除旧结果和旧确认。
- 未回应、暂离和断线都不会自动算作同意。
- 成员在线状态、跨设备状态同步、断线提示和并发版本检查。
- SVG 等分转盘、编号与完整店名清单、长名称缩写；手机结果页优先展示确认。
- 店铺新增 / 编辑 / 移出、筛选与搜索、JSON 导入导出。
- 地图搜索、结果复制分享、历史记录与餐后反馈。

## 部署结构

| 部分 | 位置与职责 |
| --- | --- |
| 前端源代码 | 根目录 `index.html`、`app.js`、`style.css`、`lib/wheel-layout.mjs` |
| GitHub Pages | `main` 分支根目录发布，`.nojekyll` 保证静态资产原样提供 |
| API 配置 | `config.js` 中公开的服务地址；不包含密钥 |
| 在线 API | `cloud/api.mjs`，支持 GitHub 入口跨域访问 |
| 房间规则 | `lib/room-service.mjs`、`lib/decision.mjs` |
| 云端部署工程 | `online/`，Sites + Cloudflare Worker + D1 |
| 本地运行 | `server.mjs`，保留无需云端的局域网模式 |

在线饭局由云数据库持久化。更新使用版本比较后写入，兼容同一轮候选的同时认可、同一结果的同时确认。具体预算与排除表单不会返回给其他成员；其他成员能看到共同候选和状态。邀请代码不能替代成员凭证读取私有房间状态。

房间在最后一次操作后保留 30 天；系统定期在请求中清理过期数据。事件记录用于分析决策流程，保留约 30 天，不公开提供浏览接口。店铺、默认偏好和本机参与身份保存在各浏览器 LocalStorage；清除浏览器数据会丢失本机身份。开发时的本地 JSON 数据没有上传到公网或 GitHub。

## 本地运行

需要 Node.js 22.13+，根目录没有 npm 依赖：

```sh
npm start
```

打开 http://localhost:4173 。macOS 可双击 `启动食光转盘.command`。

本地服务会提供自己的本地配置，即使 GitHub 的 `config.js` 指向公网，本地模式仍使用本机 JSON 数据。邀请本地朋友时需同一局域网并保持服务运行；公网正式入口不受此限制。

- `PORT=4180 npm start`：换端口。
- `HOST=127.0.0.1 npm start`：仅本机访问。
- 店铺 / 身份数据：浏览器 `fw2-*`。
- 本地饭局与事件：`data/food-wheel.json`，已被 Git 忽略。
- 旧版同源的 `food-wheel-data` 会被识别为店铺库；不同网页源之间的 LocalStorage 不共享。

## 检查与测试

```sh
npm run check
npm test
npm run report
```

20 项自动化测试覆盖：硬约束、空候选、成员未提交、认可失效、操作权限、完整房间流程、状态持久化、1–60 个候选的转盘几何、在线 API 跨域、实际 SQL 存储的并发写入、请求大小与速率限制。

`report` 分析本地 JSON 记录，自动排除纯示例与单人饭局。它不读取云端运营数据。点击确认和地图跳转不等同于实际就餐；实际采纳以餐后反馈为准。

## 维护在线版本

- 仅改 GitHub 前端：修改根目录源码并推送 `main`，GitHub Pages 会更新；接口保持兼容时无需重发服务。
- 更新备用入口中的前端快照：在 `online/` 运行 `node scripts/sync-food-wheel.mjs`，再构建并通过 Sites 发布。
- 修改在线 API / 规则：先修改根目录的 `cloud/` 与 `lib/`，同步到 `online/`，运行测试，再发布云端。
- 数据库结构在 `online/db/schema.ts`；用 `npm run db:generate` 生成新迁移。已应用的迁移不可修改或重放。
- Sites 工程 ID 在 `online/.openai/hosting.json` 中，后续发布应复用这个工程，不重复创建。
- GitHub Pages 本身不运行 Node.js；不要删除 `config.js` 的在线 API 配置，否则公网多人功能将不可用。

云端工程构建需要先在 `online/` 安装其锁定依赖。`online/` 的依赖只用于维护云端部署，日常访问网页无需安装。

## 已知范围

没有 AI 模型或菜品成分识别，没有实时营业 / 排队数据；地图为店名与地址搜索。创建的饭局保留当时店铺快照，暂不支持在同一饭局内追加新店。原版小游戏保留在旧版源码中，没有迁移到新的共同决策主流程。
